## 0. 一页结论

### 0.1 产品现状

丰麟云面已经不是一个「功能缺口型」产品：模板 → 简历 → JD 匹配 → 模拟面试 → 报告 → 复盘 → 题库 → 记忆曲线复习，五段闭环全部有真实页面、真实接口和真实数据流转，且对模型不可用做了本地降级与来源标注。当前更值得投入的方向不是继续加页面，而是三件事：

1. **把长任务做稳**：单题反馈与面试报告仍在 HTTP 请求内同步调用模型，而平台网关约 30 秒截断；`/ai/suggestions` 已经改成异步任务，但 `/answer`、`/finish` 还没有。
2. **把数据做可恢复**：作答草稿不落盘、简历切换会静默丢弃草稿、覆盖导入不可逆、删除面试会留下孤儿关联行。这些不是体验细节，是会直接丢用户成果的问题。
3. **把已有数据用得更深**：投递没有阶段历史、简历没有版本谱系、面试反馈没有可聚合的薄弱标签、JD 没有技能标签。数据维度一补，成长曲线、漏斗、训练计划、岗位对比都能自然长出来。

### 0.2 最值得先做的 8 件事

| 顺序 | 事项 | 对应条目 | 一句话理由 |
|---|---|---|---|
| 1 | 单题反馈 / 面试报告改异步任务 + 轮询 | PERF-07 | 与平台 30 秒网关约束直接冲突，是当前最大的功能性风险 |
| 2 | 读接口停止写库，`markDirty` 仅在真正变更时触发 | PERF-03、PERF-04 | 打开题库/复习/档案页会触发 O(N) 空写 + 全库导出 |
| 3 | 作答与报告提交原子化 | FUNC-01 | 并发双击/重试可能生成重复题目与重复报告 |
| 4 | 作答草稿自动保存、上下文切换保护 | UX-01、UX-02 | 刷新或切换简历会直接丢失用户刚写的内容 |
| 5 | 哈希静态资源加长缓存 | PERF-02 | 线上已 gzip，但 `Cache-Control: no-store`，重复访问仍重新下载 113.5 KB JS |
| 6 | 删除面试/复盘时清理 `application_link` | FUNC-02 | 孤儿关联会让投递详情的数量与列表不一致 |
| 7 | 覆盖导入前强制先导出当前数据 | UX-12 | 覆盖不可撤销，当前只有文字提示，没有硬保护 |
| 8 | 主包按路由拆分 | PERF-01 | 主 JS 364 KB（gzip 113.5 KB），所有页面静态导入，首屏不需要全部加载 |

### 0.4 明确不做的方向

以下方向与已知平台约束冲突，本规划不提出：账号体系与登录、云端同步、多人协作、服务端定时任务、依赖持久卷的文件上传、跨实例共享缓存/任务队列、外部数据库或向量库。所有新增数据都必须能随 JSON 备份导出/导入，所有「定时」都只能是打开页面时的客户端提醒。

### 1.3 已经做得好的部分（规划应保留）

- **降级完整**：JD 匹配、出题、单题反馈、报告都有本地规则降级，并在 UI 用 `SourceBadge` 标注「AI 生成 / 本地降级 / 常见题」。
- **输出契约严格**：所有模型输出经 zod 校验，解析/结构错误会回灌重试，不信任模型输出。
- **演示数据安全**：`demo_seed` 按 `(kind, ref_id)` 登记，清空只删登记记录，不整表删除。
- **备份事务化**：导入先 preview 再 commit，单事务写入，失败回滚；版本、条目上限、字段类型、重复 ID 都在写库前校验。
- **可访问性基础好**：Modal 焦点圈闭、Esc 关闭、移动端抽屉 inert、`prefers-reduced-motion`、`aria-live`、跳过导航链接。
- **PDF 处理边界清晰**：电子版 PDF 本地抽文字，扫描件才发视觉模型；PDF chunk 已独立，不会拖累首屏。

### 1.4 平台约束与设计边界

| 约束 | 对规划的直接影响 |
|---|---|
| 无状态容器、无持久卷、文件系统临时且重启清空 | 不做服务端长期存储、上传、队列；新增表必须可 JSON 备份；页面要明确「重启清空」 |
| 多实例不共享本地数据 | 内存任务、SQLite 任务都只能保证单实例；异步任务持久化只能解决重启/内存丢失，不能解决跨实例路由 |
| 凭据只能放全局环境变量 | 不引入需要新密钥的第三方服务；不做账号体系 |
| 无账号体系 | 不做登录、权限、多人协作、云端同步；分享只能是自包含文件或 URL 片段 |
| LLM 网关约 30 秒截断 | 长任务必须异步化或拆分；同步接口只做短请求 |
| 数据靠 JSON 备份导出/导入 | 任何新增表/字段都要同步升级 `backup.ts` 版本、校验、LIMITS，以及 `demo.ts` 清理逻辑 |

## 2. 现有功能的细节优化

编号规则：`UX-*` 用户体验，`PERF-*` 性能与可靠性，`FUNC-*` 功能完整性。成本：S ≤ 0.5 人日，M 1–3 人日，L 3–7 人日。优先级：高 / 中 / 低。

### 2.1 用户体验（UX）

#### UX-01 / UX-02 / UX-06 的落地要点

这三项都属于「不改变产品逻辑，只补状态持久化与保护」的改动，建议同一批做：

- **统一草稿键**：`fenglin:answer:{interviewId}:{turnId}`；简历优化用 `fenglin:optimize:{resumeId}:draft`。写入节流 500ms，避免每次按键都写。
- **恢复提示**：恢复时不要静默覆盖用户新输入，显示一条可关闭的 `Callout`：「已恢复 2 分钟前的草稿」。
- **计时基准**：把 `turnStartedAt` 存进组件 ref 即可，不需要后端字段；但如果后续要做「答题用时统计」（DATA-06），再把它写入 `interview_turn.answer_started_at`。

#### PERF-07 的落地设计（最高优先）

现状：`/ai/suggestions` 已经证明「202 + 轮询」能在 30 秒网关下稳定工作。反馈与报告应完全复用这套模式，而不是继续赌模型在 30 秒内返回。

建议接口：

```
POST /api/interviews/:id/answer
  body: { turnId, answer }
  202 -> { jobId, status: 'pending' }

GET /api/interviews/:id/jobs/:jobId
  -> { status: 'pending' | 'done' | 'error',
       feedback?, nextTurn?, allDone?, session?, error? }

POST /api/interviews/:id/finish
  202 -> { jobId, status: 'pending' }

GET /api/interviews/:id/jobs/:jobId
  -> { status, report?, session?, error? }
```

服务端要点：

- 任务开始前先做**原子占位**（见 FUNC-01），避免同一题被两个任务同时处理。
- 任务状态写 `ai_job`（PERF-08），不要只放内存。
- 轮询接口只读任务状态，不再调用模型。
- 任务过期（如 10 分钟）返回明确错误，前端提示重新提交。
- 前端 `InterviewSession.tsx` 把 `submit` 与 `finish` 改成「提交 → 轮询 → 更新 session」，保留当前 `BusyProgress` 与失败重试入口。

验收：

- 构造一次 3 次重试、总耗时 > 30 秒的模型调用，页面仍能拿到结果。
- 两次并发提交同一题，只产生一条反馈与一个下一题。
- 任务进行中刷新页面，重新进入后能继续轮询并恢复结果（配合 UX-01）。

#### PERF-03 / PERF-04 的落地要点

`ensureReviewTasks()` 的目标是「给历史题目补排程」，不是每次请求都重扫全表。建议改成：

```sql
-- 只找还没有排程的题库
SELECT b.id, b.weak, b.last_practiced_at, b.created_at
FROM bank_item b
LEFT JOIN review_task t ON t.kind = 'bank' AND t.ref_id = b.id
WHERE t.kind IS NULL;

-- 复盘同理
SELECT r.id, r.rating, r.created_at
FROM review r
LEFT JOIN review_task t ON t.kind = 'review' AND t.ref_id = r.id
WHERE t.kind IS NULL;
```

这样查询本身走索引，返回 0 行时不需要任何 `INSERT`，也就不会触发 `markDirty`。`db.run()` 再加 `changes > 0` 判断，双保险。

#### FUNC-01 的推荐实现

最小改动、最稳的顺序：

```ts
// 1. 原子占位：只有一个请求能把 answer 从 NULL 改为非 NULL
const claim = db.prepare(
  'UPDATE interview_turn SET answer = ?, answered_at = ? WHERE id = ? AND interview_id = ? AND answer IS NULL'
).run(answer, nowIso(), turnId, id);
if (claim.changes === 0) throw new HttpError(409, '这道题已经作答过了');

// 2. 再调用模型、写 feedback；失败时把 answer 回滚为 NULL 或保留为待重试状态
// 3. 生成下一题前再次确认当前 turn 仍是本次占位的那条
```

`/finish` 同理：先 `UPDATE interview SET status = 'finishing' WHERE id = ? AND status = 'active'`，`changes=0` 直接返回已有报告或 409。这样即使前端重复点击、网络重试，也只有一个请求能进入模型调用。

#### FUNC-09 的推荐数据设计

```sql
CREATE TABLE IF NOT EXISTS application_stage_log (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  application_id INTEGER NOT NULL REFERENCES application(id) ON DELETE CASCADE,
  from_stage     TEXT,
  to_stage       TEXT NOT NULL,
  note           TEXT NOT NULL DEFAULT '',
  changed_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_stage_log_app ON application_stage_log(application_id, changed_at);
```

- 新建投递时写一条 `NULL -> applied`。
- 修改阶段时，只有 `stage` 真的变化才写日志。
- 统计口径改为：
  - 曾进入面试 = 日志中出现过 `interview1/interview2/hr/offer`；
  - 曾获 offer = 日志中出现过 `offer`；

- 备份 v2 必须包含该表；`demo.ts` 清理也要按 `application_id` 删除。

## 3. 现有能力的拓展方向

这一节不重复第 2 节的「修问题」，而是回答：在现有闭环上，哪些能力可以自然延伸、哪些流程可以补齐、哪些数据维度值得补。

### 3.1 功能分支延伸

#### 3.1.1 简历：从「多份文本」到「版本树 + 岗位定制」

现状：`resume` 表只有 `title/content/job_id/source`，`Optimize.tsx` 的「另存新版」只是再插一条记录。用户有多份简历，但不知道谁派生自谁、哪份投过哪个岗位。

可延伸：

- **版本树**：`resume.parent_id` + `version_label`；`Resumes.tsx` 按 `parent_id` 分组展示，标注「初稿 / 迭代 3 / 岗位定制版」。
- **两版对比**：新增 `/resumes/compare?a=1&b=2`，复用 `lib/diff.ts` 的 `diffLines`，并排显示新增/删除；对比结果可复制为「改动说明」。
- **按岗位推荐版本**：用 `jd_analysis` 的历史分数，在投递详情里推荐「这份岗位历史匹配度最高的简历」。
- **面试用错版本防护**：`Interviews.tsx` 开始面试前显示当前简历标题与更新时间，若超过 30 天未更新则提示。

落点：`db.ts` 的 `resume` 表、`core.ts` 的 `/resumes`、`Resumes.tsx`、新增 `ResumeCompare.tsx`。优先级中，成本 L，依赖 FUNC-05。

#### 3.1.2 岗位与 JD：从「一段文本」到「可比较的技能要求」

现状：`job` 只有 `title/company/jd`；JD 匹配是一次性的 `jd_analysis`。岗位之间无法比较，JD 里的技能要求无法沉淀。

可延伸：

- **技能标签**：从 JD 抽取 6–12 个技能/能力项，存 `job_skill(job_id, skill, weight, source)`；匹配分析时按标签展示覆盖率。
- **多 JD 对比**：选两个岗位，比较共同要求、差异要求、简历覆盖情况；复用 `diffLines` 或表格。
- **岗位状态**：`status`（开放/已投/已关闭）、`priority`（高/中/低）、`deadline`、`location`、`salary_range`、`source_url`。
- **JD 版本**：同一岗位多次修改时保留 `job_jd_version`，方便回看「当时投的是哪版 JD」。

落点：`Jobs.tsx`、`core.ts` 的 `/jobs`、新增 `JobSkills.tsx`、`job_skill` 表。优先级中，成本 M，依赖 DATA-03 / DATA-07。

#### 3.1.3 面试：从「固定四轮」到「可配置训练模式」

现状：`interview-plan.ts` 固定 `intro/professional/behavioral/reverse` 四轮；`Interviews.tsx` 只有四种出题方式；追问固定最多 2 层、阈值 72。

可延伸：

- **出题预设**：校招常规面 / 实习面 / HR 面 / 压力面 / 英文面；不同预设对应不同轮次、题量、追问强度、评分侧重点。
- **追问强度**：温和 / 标准 / 高压三档；高压档降低 `FOLLOWUP_THRESHOLD`、增加追问层数上限。
- **面试官风格**：结构化 / 追问型 / 压力型；通过 prompt 的 system 段控制，不影响现有评分校准。
- **专项练习**：只练「项目深挖」、只练「行为面」、只练「反问」；复用 `mode = 'bank'` 的抽题机制。
- **报告导出**：见 FUNC-03。

落点：`server/interview-plan.ts`、`server/prompts.ts`、`Interviews.tsx`、`InterviewSession.tsx`。优先级中，成本 M。

#### 3.1.4 复盘与题库：从「记录」到「可练习的卡片」

现状：`review` 是自由文本；`bank_item` 只有题面/分类/薄弱；复习只做自评。

可延伸：

- **答题框架卡**：为每道题生成「考察点 / 答题框架 / 常见坑 / 可追问点」，存 `question_card`（或 `bank_item.card_json`）。
- **复盘标签体系**：把 `tags` 从自由文本改为「固定标签 + 自定义」；固定标签如 STAR、量化、项目细节、数据来源、个人贡献、表达节奏。
- **题库批量导入/导出**：CSV / Markdown（`## 分类` + 每行一题），复用模板导入的解析思路。
- **复习作答**：见 FUNC-15；复习结果写回 `last_score` 与 `review_task`。

落点：`Bank.tsx`、`Reviews.tsx`、`review.ts`、新增 `question_card` 表。优先级中，成本 M。

#### 3.1.5 投递：从「当前阶段」到「求职漏斗」

现状：`application` 只有当前 `stage`，统计是快照；`Applications.tsx` 明确提示口径偏差。

可延伸：

- **阶段历史**：见 FUNC-09。
- **漏斗视图**：投递 → 笔试 → 一面 → 二面 → HR → offer，显示每一层数量与转化率；可按公司/岗位/月份筛选。
- **跟进日历**：`next_action_at` + 日历视图；训练台显示「今天要跟进」。
- **offer 对比**：多家 offer 的薪资、地点、团队、成长性做一张对比表（纯本地数据）。
- **投递与简历版本关联**：记录这次投递用的是哪份简历，反查该版本的历史匹配分。

落点：`Applications.tsx`、`applications.ts`、`Home.tsx`、新增 `application_stage_log`。优先级高，成本 L。

### 3.2 交互流程完善

#### 3.2.1 「报告 → 复盘 → 题库 → 计划」一键链

现状：报告页可以「生成复盘草稿」，复盘页可以「加入题库」，题库页可以「再练」，但四步之间需要用户自己找入口。

建议：

- 报告页底部增加一条流程条：`生成复盘草稿 → 补改进点 → 加入题库 → 安排 7 天复习`，每一步完成后打勾。
- 复盘保存后，直接提供「加入题库并安排复习」按钮。
- 题库复习完成后，回到训练台显示「今日已完成」。
- 与 MOD-03（7 天训练计划）打通：报告中的 `weaknesses` 自动变成计划任务。

落点：`InterviewReport.tsx`、`Reviews.tsx`、`Bank.tsx`、`Home.tsx`。成本 M，优先级高。

#### 3.2.2 「建议 → 应用 → 对比 → 另存」简历链

现状：`Optimize.tsx` 的建议只能复制；改完要手动对比、手动另存；导出读取已保存版本。

建议：

- 每条建议增加「应用到草稿」与「撤销」。
- 应用后自动切到「对比原始」视图，显示本条第几处改动。
- 全部改完后显示「另存为新版本」吸底按钮；保存后自动刷新简历列表与当前上下文。
- 导出区读取当前草稿，若未保存则先提示（UX-05）。

落点：`Optimize.tsx`。成本 M，优先级高。

#### 3.2.3 上下文切换保护

现状：顶部栏与工作台都能切换简历/岗位；`Optimize` 切换会清空草稿与结果；`InterviewSession` 切换岗位不会影响当前场（因为已落库），但用户可能误以为会。

建议：

- 全局：切换当前简历/岗位时，如果有未保存草稿，统一弹确认。
- 面试中：顶部上下文选择器禁用或标注「本场已锁定」。
- 面试列表：开始新面试时显示「将使用：简历 X / 岗位 Y」，避免选错。

落点：`Layout.tsx`、`Optimize.tsx`、`InterviewSession.tsx`、`Interviews.tsx`。成本 S，优先级高。

#### 3.2.4 失败可恢复

现状：AI 失败有重试入口，但长任务离开页面就丢；提交失败会保留答案，但刷新就丢。

建议：

- 所有 AI 任务统一「任务 ID + 轮询 + 可恢复」；页面离开不取消任务，回来继续查。
- 所有长文本输入（答案、复盘、简历草稿）本地自动保存。
- 失败时保留输入，给出「重试 / 改用本地降级 / 复制内容」三个出口。

落点：`api.ts`、`Optimize.tsx`、`InterviewSession.tsx`、`Reviews.tsx`。成本 M，优先级高。

#### 3.2.5 客户端提醒

现状：没有提醒；记忆曲线只在打开题库页时显示。

建议：

- 打开应用时检查：今日待复习、投递跟进到期、备份超过 7 天。
- 训练台显示一张「今日要做」卡片，按优先级排序。
- 可选浏览器通知（用户授权后），只在页面打开时触发，不做服务端推送。

落点：`Home.tsx`、`Bank.tsx`、`Applications.tsx`、`Backup.tsx`。成本 S/M，优先级中。

## 4. 新增关联功能模块

每个模块都遵守同一约束：数据存本地 SQLite，随 JSON 备份迁移；不做账号、不做云端、不做服务端定时任务。模块必须能落回现有闭环，而不是孤立的新页面。

### MOD-01 STAR 经历素材库

- **应用场景**：学生「不知道简历写什么」「面试一问项目就只会说做了什么」。把一段经历拆成情境（S）、任务（T）、行动（A）、结果（R）、指标、个人贡献，形成可复用素材卡。
- **核心价值**：一次录入，三处复用——简历 bullet、自我介绍、面试答题/追问。解决「素材贫乏」这个上游问题。
- **与现有功能联动**：
  - `TemplateBuild`：每栏旁边提供「从素材库插入」；
  - `Optimize`：建议应用时优先引用素材卡中的量化结果；
  - `InterviewSession`：出题 prompt 可带入 1–2 张相关素材卡，追问更具体；
  - `Reviews`：复盘时把「当时没答好的点」补回素材卡。
- **落点**：新增 `/experiences` 页面（`src/pages/Experiences.tsx`）；API `/api/experiences` CRUD；表 `experience_card`；备份 v2。
- **成本/优先级**：L / 高；依赖 DATA-05。

### MOD-02 自我介绍与背稿卡

- **应用场景**：每场面试第一题；不同时长（60/90/120 秒）、不同岗位需要不同版本。
- **核心价值**：把「第一题」从临场发挥变成可准备的结构；支持朗读与计时，形成肌肉记忆。
- **与现有功能联动**：读取当前简历、目标岗位、`experience_card`；生成 3 个时长版本；可在面试 `intro` 轮次前预览；可加入题库「自我介绍」分类；可打印成卡片。
- **落点**：新增 `/pitch`（`src/pages/Pitch.tsx`）；API `/api/pitch/generate`（异步任务，复用 PERF-07 模式）；草稿存 `localStorage`；可选存 `pitch_version` 表。
- **成本/优先级**：M / 高；依赖 MOD-01（可选，素材越全效果越好）。

### MOD-03 7 天训练计划

- **应用场景**：报告给了薄弱点，但用户不知道怎么安排接下来一周；题库复习到期日分散，容易忘。
- **核心价值**：把「一次性模拟」变成「持续训练」；提升回访与完成率；让报告里的建议真正被执行。
- **与现有功能联动**：
  - 读取最近一场报告的 `weaknesses` 与 `reviewPoints`；
  - 读取 `review_task` 今日到期；
  - 读取投递的 `next_action_at`；
  - 生成每天 1–3 个任务（练 2 道薄弱题 / 重答 1 个追问 / 更新简历 1 段 / 跟进 1 个投递）；
  - 完成任务后写 `training_task.status`，训练台显示进度。
- **落点**：新增 `/plan`（`src/pages/Plan.tsx`）；API `/api/plan/today`、`/api/plan/:id/complete`；表 `training_task`；备份 v2。
- **成本/优先级**：M / 高；依赖 FUNC-10、DATA-08。

### MOD-04 投递日历与跟进

- **应用场景**：投递多家公司后，笔试、面试、HR 面、offer 截止日期散落；容易漏跟进。
- **核心价值**：把投递从「列表」变成「时间轴 + 日历」；配合阶段历史，形成真正的求职漏斗。
- **与现有功能联动**：`application_stage_log` 提供时间线；`next_action_at` 提供提醒；训练台「今日跟进」；岗位 `deadline` 提供截止提醒；面试/复盘关联已有。
- **落点**：`Applications.tsx` 增加「看板 / 日历」切换；API `/api/applications/calendar?from=&to=`；不需要新表，依赖 FUNC-09/10。
- **成本/优先级**：M / 高；依赖 FUNC-09、FUNC-10。

### MOD-05 简历版本对比工作台

- **应用场景**：同一岗位改了三版，不知道最新版比上一版强在哪；面试时用错版本。
- **核心价值**：让「版本」成为可管理对象，而不是一堆同名简历；对比结果可直接作为「改动说明」写进复盘。
- **与现有功能联动**：`resume.parent_id` 版本树；`lib/diff.ts` 行级 diff；`jd_analysis` 分数对比；投递记录关联 `resume_id`；面试记录关联 `resume_id`。
- **落点**：新增 `/resumes/compare?a=&b=`（`src/pages/ResumeCompare.tsx`）；API `/api/resumes/:id/diff/:otherId`；`Resumes.tsx` 增加「对比」入口。
- **成本/优先级**：M / 中；依赖 FUNC-05、DATA-02。

### MOD-06 岗位技能图谱

- **应用场景**：JD 很长，不知道哪些是硬要求；多个岗位之间不知道如何取舍。
- **核心价值**：把 JD 从「一段文字」变成「技能标签 + 权重 + 简历覆盖率」；指导简历补强、题库分类、面试出题。
- **与现有功能联动**：
  - `jd-match` 的 `covered/missingKeywords` 可直接映射为技能标签；
  - `resume` 文本做关键词覆盖；
  - `bank_item.category` 可按技能重组；
  - `interview` 出题时优先问缺失技能；
  - 多岗位对比时展示共同/差异要求。
- **落点**：新增 `/jobs/:id/skills`（`src/pages/JobSkills.tsx`）；API `/api/jobs/:id/skills`（LLM 异步 + 本地关键词兜底）；表 `job_skill`；备份 v2。
- **成本/优先级**：M / 中；依赖 DATA-03。

### MOD-07 题目解析卡

- **应用场景**：题库只有题面，复习时不知道从哪说起；面试被追问时没有框架。
- **核心价值**：每题生成「考察点 / 答题框架 / 常见坑 / 可追问点 / 参考要点」，把题库从「题目列表」变成「可学习卡片」。
- **与现有功能联动**：`bank_item` 详情弹窗；`common-questions` 也可生成；`review` 复盘时引用；`InterviewSession` 追问方向可引用卡片中的「可追问点」。
- **落点**：`Bank.tsx` 增加「解析卡」按钮；API `/api/bank/:id/card`（异步）；表 `question_card` 或 `bank_item.card_json`；备份 v2。
- **成本/优先级**：M / 中；依赖题库数据。

### MOD-08 英文面试模式

- **应用场景**：外企、英文项目面、留学申请面试；现有产品全中文。
- **核心价值**：同一套闭环支持英文出题、英文作答、英文反馈；复用现有评分与追问逻辑，不新建一套系统。
- **与现有功能联动**：
  - `interview.mode = 'english'` 或 `seed_json.language = 'en'`；
  - `prompts.ts` 增加英文 system/user 模板；
  - `tts.ts` 选择 `en-*` 语音；
  - `speech.ts` 设置 `rec.lang = 'en-US'`；
  - 报告可中英双语；
  - 题库增加「英文」分类。
- **落点**：`Interviews.tsx` 增加语言选项；`interview-plan.ts`、`prompts.ts`、`tts.ts`、`speech.ts`；无需新表。
- **成本/优先级**：M / 中；依赖现有面试链路。

### MOD-09 压力面 / HR 面专项

- **应用场景**：行为面、HR 面、压力面与普通技术面差异很大；现有固定四轮无法覆盖。
- **核心价值**：用预设快速进入特定训练场景；追问强度、评分侧重点、面试官语气都可调。
- **与现有功能联动**：`interview-plan.ts` 的 `ROUNDS` 改为可按 preset 生成；`InterviewSession` 展示当前 preset；报告按 preset 调整 `roundScores`；题库可按 preset 筛选。
- **落点**：`Interviews.tsx` 增加 preset 选择；`interview-plan.ts` 增加 `PRESETS`；`interview.seed_json` 记录 preset；无需新表。
- **成本/优先级**：M / 中；依赖 3.1.3。

### MOD-10 求职周报与洞察

- **应用场景**：一周下来不知道做了什么、进展如何；答辩/复盘需要一份阶段总结。
- **核心价值**：自动汇总本周面试、投递、复盘、复习、成长变化；形成可导出的周报；长期看趋势。
- **与现有功能联动**：
  - `interview` 本周完成数与分数变化；
  - `application` 本周新增/阶段变化（依赖 FUNC-09）；
  - `review`/`bank` 本周新增与复习完成；
  - `growth` 本周总分/三维变化；
  - 输出 Markdown + 打印视图。
- **落点**：新增 `/weekly`（`src/pages/Weekly.tsx`）；API `/api/reports/weekly?from=&to=`；复用 `PrintProfile` 的打印样式；无需新表（阶段历史上线后更准）。
- **成本/优先级**：S/M / 中；依赖 FUNC-09。

### MOD-11 只读分享快照

- **应用场景**：把面试报告/求职档案发给老师、同学或面试教练看，但产品没有账号、没有持久存储，不能做在线分享链接。
- **核心价值**：生成一个**自包含 HTML 文件**（内嵌数据与样式），对方双击即可查看；不依赖服务器存储，不产生新的隐私面。
- **与现有功能联动**：`InterviewReport` 与 `PrintProfile` 增加「导出分享快照」；复用现有打印样式；数据来自当前接口；导出前明确提示包含简历/作答等个人信息。
- **落点**：新增 `src/lib/share.ts`，把报告/档案数据 + 内联 CSS 拼成 HTML Blob 下载；不新增后端表；不需要 URL 短链。

## 5. 优先级、成本与迭代路线

### 5.1 评分口径

- **优先级**
  - 高：影响数据安全、任务成功率和核心闭环；不做会持续产生用户可见问题。
  - 中：明显提升效率或数据价值，但不阻塞主流程。
  - 低：锦上添花，可在资源允许时做。
- **成本**
  - S：≤ 0.5 人日，通常是前端状态、样式、单个接口字段。
  - M：1–3 人日，涉及一个新接口、一张小表或一个页面区块。
  - L：3–7 人日，涉及异步任务、数据迁移、跨页面联动。
- **收益**
  - 用可验证指标描述：失败率、丢失率、P95 延迟、首屏体积、步骤数、可查询数据量。

### 5.4 验收指标

工程侧：

- AI 长任务成功率 ≥ 99%（排除模型服务整体不可用）；30 秒网关导致的失败为 0。
- 并发重复提交产生重复数据为 0。
- `/bank`、`/review-plan/today`、`/dossier` 不再产生写事务。
- 备份 v2 导出 → 清空 → 导入，条目数、关联、排程完全一致。
- 删除面试/复盘后无 `application_link` 孤儿行。
- 首屏 JS（gzip）在路由拆分后下降 ≥ 40%；重复访问 `/assets/*` 命中缓存。

产品侧：

- 「报告 → 复盘 → 题库 → 计划」主链可在 3 次点击内完成。
- 简历「建议 → 应用 → 对比 → 另存」可在同一页面完成。
- 投递漏斗可按历史阶段计算「曾进入面试」「曾获 offer」。
- 7 天计划每天有 1–3 个可执行任务，完成后有反馈。
- 分享快照可离线打开，且不包含任何服务端链接。

### 5.5 风险与应对

| 风险 | 应对 |
|---|---|
| 新增表导致备份不兼容 | 先做 FUNC-11（备份 v2），再落 DATA-*；导入同时接受 v1/v2 |
| 异步任务在多实例下轮询落错实例 | 文档明确当前为单实例数据模型；任务落库只解决重启丢失，不做跨实例承诺 |
| 内存限流在多实例下不共享 | 应用层限流作为兜底；多实例部署时需要在平台网关层做全局限流，或维持单实例 |
| 限流误伤真实访客 | 阈值走环境变量；先宽松（如每分钟 6 次）观察，再收紧 |
| 阶段历史增加写入 | 只在 `stage` 真正变化时写；与投递更新同一事务 |
| LLM 成本上升 | 任务级缓存 + 每日上限 + 失败不重试超过 2 次；长文本先截断再调用 |
| 分享快照泄露 PII | 默认不包含联系方式；导出前明确提示；文件名带日期；不做公开链接 |

### 5.6 明确不做清单

- 账号、登录、权限、团队空间。
- 云端同步、跨设备实时同步、服务端持久化上传。
- 服务端定时任务、消息推送、邮件提醒。
- 依赖持久卷的录音/视频存储。
- 跨实例共享的任务队列、缓存、向量库。
- 用 AI 编造学生没有的经历或数据（现有 prompt 已明确禁止，新增功能继续遵守）。

## 6. 落地检查清单

### 6.1 每次新增表/字段

1. `app/server/db.ts`：`CREATE TABLE IF NOT EXISTS` 或 `PRAGMA table_info` + `ALTER TABLE` 兼容旧库；补索引。
2. `app/server/routes/backup.ts`：`BACKUP_VERSION` 升级；导出包含新表；preview/import 校验字段、类型、条目上限；v1 兼容。
3. `app/server/routes/demo.ts`：示例数据写入时登记 `demo_seed`；清空时按登记删除；新增 kind 加入 `Kind` 与 `KIND_LABEL`。
4. `app/src/types.ts`、`app/src/api.ts`：类型与接口封装。
5. 对应页面：空态、加载态、错误态、移动端布局。
6. 文档：`README.md` 的功能地图与已知限制同步更新（如果用户要求改文档；否则至少在规划文档标注）。

### 6.2 每次新增 AI 能力

- 输出必须有 zod schema；失败有本地降级或明确错误。
- 预计 > 20 秒的任务走「202 + 轮询」，不要在 HTTP 请求内同步等待。
- prompt 中明确「不得编造原文没有的数据」；缺数据用「待补充：xx」占位。
- UI 用 `SourceBadge` 标注 AI / 本地 / 常见题来源。
- 记录耗时与失败码，便于后续调 prompt 与超时。

### 6.3 每次改前端交互

- 真实浏览器验证桌面（1440）与手机（390）两档。
- 检查空态、加载态、错误态、权限/降级态。
- 长文本输入要有草稿保存或离开确认。
- 破坏性操作要有二次确认；不可逆操作要先导出。
- 不引入新的 UI 库；继续使用 `components/ui.tsx` 的 Button/Card/Modal/Field 等。

### 6.4 建议埋点（本地统计即可）

由于没有账号与后端分析服务，建议把关键事件写入 `setting` 或 `localStorage`，用于演示与自测：

- AI 任务：类型、耗时、成功/失败、重试次数。
- 面试：开始/完成/放弃、平均答题时长、追问触发率。
- 简历：建议生成次数、应用建议次数、另存版本次数。
- 投递：阶段变更次数、跟进完成率。
- 备份：导出/导入次数、最近导出时间。

这些数据不用于商业分析，只用于验证优化是否生效。
