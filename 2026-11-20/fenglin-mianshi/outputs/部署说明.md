## 三、公网部署方式（trae-remote-official:deployment）

应用形态：**FunctionWeb（nodejs20）**——单个 Node 进程同时提供前端静态文件与 `/api`，具备真实服务端，能安全放置模型密钥。

| 项 | 值 |
|---|---|
| 部署类型 | `function-web`（DeployType=2） |
| 构建脚本 | `build.sh`（`npm ci` → `npm run build` → 产物校验 → `npm prune --omit=dev` → 组装 `dist/`；保留 `app/public/`，由 Vite 复制进 `dist/`） |
| 输出目录 | `dist` |
| 启动脚本 | `dist/run.sh`（显式 `NODE_ENV=production`、`PORT=8000`、`TMPDIR`，再 `node server/index.js`；`SHARED_DEMO=1` 由执行配置注入） |
| 监听端口 | 8000，绑定 `0.0.0.0` |
| 运行时环境变量 | `ZHIPU_API_KEY`、`ZHIPU_MODEL=glm-4-air`、`SHARED_DEMO=1`；可选 `AI_RATE_LIMIT_PER_MIN`（默认 6）、`AI_DAILY_LIMIT`（默认 300） |
| 资源 | 1 CPU / 2 GiB，最多 10 实例 |

运行时环境变量只存在执行配置里，**不进入上传包**；上传包也不含 `.env`。部署完成后检查过线上 JS 产物，不包含密钥字符串。

### 构建脚本要点（`build.sh`）

```sh
#!/bin/sh
set -eu
export NPM_CONFIG_REGISTRY='https://registry.npmjs.org/'
npm ci --registry='https://registry.npmjs.org/'
test -f node_modules/sql.js/dist/sql-wasm.wasm   # 确保 WASM 存在
npm run build
test -f dist/index.html
test -f dist/brand/logo.png          # 品牌资源产物校验
test -f dist/brand/favicon-128.png   # 站点图标产物校验
npm prune --omit=dev
mkdir -p dist/server
cp -R dist-server/. dist/server/
cp package.json dist/package.json
cp -R node_modules dist/node_modules
cp run.sh dist/run.sh
chmod 755 dist/run.sh
```

说明：运行根目录是 `dist/`，Node 只能从 `dist/node_modules` 解析依赖，因此必须把生产依赖复制进去；否则启动会 `MODULE_NOT_FOUND`。`app/public/` 不能删也不能排除，`dist/brand/` 下的 LOGO 与 favicon 都来自它。

### 2026-11-22 P0 部署：run.sh 三处修正与缓存头实测

当前在线版本为 `dep_6b025af6bf08a7670a7c2f3e`。这次除应用侧改动外，`run.sh` 修正了三处，都是「不修就必坏」的问题：

| 修正 | 原因 | 不修会怎样 |
|---|---|---|
| 显式 `export NODE_ENV=production` | 平台不保证注入该变量；应用只在 production 下把数据库放到 `TMPDIR` | 数据库会落到只读的 `/opt/bytefaas/data`，写库报 `EROFS/EACCES` |
| 显式 `export PORT=8000` | 平台未注入 `PORT` 时应用回退到 8787 | 平台按 8000 探活，实例监听 8787，整站不可用 |
| 设置 `TMPDIR` | sql.js 落盘与临时文件需要可写目录 | 落盘路径不确定，重启/清理行为不可控 |

`build.sh` 侧保留并补全了产物校验：`dist/index.html`、`dist/brand/logo.png`、`dist/brand/favicon-128.png` 任一缺失即构建失败（`public/` 会被 Vite 复制到 `dist/` 根，品牌资源漏带会重现 LOGO 空白）。

**缓存头实测（如实记录，未达成）**：应用层对 `/assets/*` 设置了 `Cache-Control: public, max-age=31536000, immutable`，本地同代码验证为 `immutable`；但线上响应头实测仍是 `Cache-Control: no-store`，被平台 CDN 网关（volc-dcdn / Trae Hecate Gateway）覆盖。因此「哈希资源长缓存」在线上**没有生效**，重复访问不会命中长期缓存；这条保留为已知限制，不在应用层继续做无效补偿。

### 本轮新增接口与依赖（部署形态未变）

- 新增接口：
  - `POST /api/jobs/fetch-jd`：JD 链接服务端代抓；仅公网 http/https，3 次重定向、10 秒超时、1.5 MB 上限，DNS 校验拒绝内网 / 回环；失败返回 `{ok:false, message}`，不写库。
  - `GET /api/common-questions`：返回 60 道内置常见题与来源说明（社区常见题型整理，非官方真题）。
  - `GET /api/backup/export`：导出完整 JSON 备份，`Content-Disposition` 文件名带日期。
  - `POST /api/backup/preview`、`POST /api/backup/import`：先校验预览再写入；导入支持合并 / 覆盖，单事务，失败回滚；请求体上限 8 MB。
  - `POST /api/interviews/:id/answer`、`POST /api/interviews/:id/finish`（2026-11-22）：改为异步任务，返回 `202 { jobId, status: 'pending' }`，前端轮询 `GET /api/interviews/:id/jobs/:jobId` 取结果；作答与出报告互斥（作答走原子占位，报告走状态条件收口），并发重复提交返回 `409`。
- 限流（2026-11-22）：对 `/ai/*` 与面试作答 / 出报告这些触发模型的接口，按 IP 每分钟次数与每日总量双阈值限流，超限返回 `429` 并带 `Retry-After`；`GET /ai/status` 豁免。阈值由 `AI_RATE_LIMIT_PER_MIN`（默认 6）与 `AI_DAILY_LIMIT`（默认 300）控制，置 0 关闭对应阈值。计数保存在进程内存，**只在单实例内生效**，多实例下各算各的。
- 依赖：**没有新增 npm 依赖**，没有新增环境变量，没有数据库结构变更（沿用 `review_task`、`demo_seed` 等既有表）。
- 网络：JD 抓取需要运行实例具备公网出站能力；其余功能仍只在服务端调用智谱接口。FunctionWeb 形态无需额外配置。

## 四、SQLite 与托管形态的兼容性取舍（重要）

| 方案 | 结果 |
|---|---|
| better-sqlite3（最初实现） | ❌ 不可用。构建机 Node 22（ABI 127）与运行时 Node 20（ABI 115）不匹配；改用 Node 20 预编译二进制后又报 `GLIBC_2.33 not found` |
| **sql.js（当前实现）** | ✅ 采用。SQLite 官方 C 代码编译出的 WebAssembly 版，无原生二进制，跨 Node 版本与 glibc 一致；表结构、SQL 语法、约束行为不变 |

只重写了 `server/db.ts` 一个文件：对外仍暴露 `prepare().get/all/run`、`exec`、`close`，路由与业务逻辑零改动。持久化策略：

- 启动时若文件存在则读入内存；文件损坏时自动备份为 `.corrupt-<时间戳>` 并新建空库，不会导致整站起不来。
- 每次写操作标脏，150ms 防抖；落盘用「写 `.tmp` → `rename`」保证原子性；进程收到 SIGINT/SIGTERM 时同步 flush。

## 五、数据持久化现状（如实说明）

| 环境 | 数据库位置 | 是否持久 |
|---|---|---|
| 本地开发 | `app/data/fenglin.sqlite` | ✅ 持久，可备份 |
| 本地生产 | `%TMPDIR%\fenglin-cloud-interview\fenglin.sqlite`（或 `DB_PATH`） | 取决于指定路径 |
| 公网托管 | `{TMPDIR}/fenglin-cloud-interview/fenglin.sqlite` | ❌ 临时：重启、重新部署、平台清理即清空；多实例之间不共享 |

**影响**：公网实例只适合演示，不能当正式产品使用。我们选择「如实告知 + 本地持久」而不是伪装持久化。

## 六、账号体系结论：不做注册登录，用文件备份替代

判定依据（托管形态的真实能力）：

1. 有可运行的 Node 服务端 → 技术上加登录接口没问题；
2. **没有持久化存储卷、没有外部数据库/对象存储** → 账号、简历、题库在重启后必然丢失；
3. 运行时环境变量是全局一份，**不能安全保存每个用户的密码/凭据**；
4. 多实例之间文件系统不共享，无法做一致的会话。

结论：在该形态下实现注册登录，只会得到「重启即丢账号、多人互相看到数据」的假账号体系。因此**维持单机档案**，并在产品上如实呈现：

- 页面顶部常驻提示条：公网演示实例、共享数据、重启清空；
- 隐私页「部署形态带来的限制」逐条写明临时存储、无多用户隔离、为何不做注册登录；
- 档案页写明「轻量方案：不做注册、不做密码、不做多用户隔离」；
- 用「数据备份」页的 JSON 导出 / 导入替代账号：用户可在重新部署前保存全部本机档案，换设备后导入继续；这不等于云同步，文件本身包含简历正文等敏感信息，需要用户自行保管。

## 八、常见故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `NODE_MODULE_VERSION 127 vs 115` | 原生模块 ABI 与运行时 Node 不匹配 | 不要用原生二进制依赖；本项目已换 sql.js |
| `GLIBC_2.33 not found` | 预编译二进制依赖更高 glibc | 同上 |
| `MODULE_NOT_FOUND: express` | 依赖没进 `dist/node_modules` | 检查 `build.sh` 是否 `npm prune` 后复制 `node_modules` |
| 健康检查超时 | 监听端口与 `runtime.port` 不一致，或只绑 `127.0.0.1` | 必须 `0.0.0.0` + 读 `PORT` |
| 写入报 `EROFS/EACCES` | 往只读目录写数据 | 所有运行期写入走 `${TMPDIR}`；并确认 `NODE_ENV=production`（只有该模式下才把库放 `TMPDIR`，否则会落 `/opt/bytefaas/data`） |
| 实例起来了但探活一直失败 | 平台没注入 `PORT`，应用监听了 8787 | `run.sh` 显式 `export PORT=8000` |
| 接口 503「AI 暂时无法给出建议」 | 模型超时或网络异常 | 页面会提示重试；JD/面试类自动降级并标注「本地降级」 |
